# Development

How to work on SYLTHARAE: the conventions the code and templates follow, and the
checks that hold them. Architecture is in [ARCHITECTURE.md](ARCHITECTURE.md),
configuration in [CONFIGURATION.md](CONFIGURATION.md), database in
[DATABASE.md](DATABASE.md), security policy in [SECURITY.md](SECURITY.md).

Agent sessions and their reviewers: see [AGENTS.md](../AGENTS.md).

## Setting up

```
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt

cp .env.example .env          # DB_* and FLASK_SECRET_KEY at minimum
python3 run_web.py            # or: FLASK_ENV=development .venv/bin/python run_web.py
```

A first start with no `.system_initialized` marker sends every request to the
installation wizard at `/setup`; that is the intended first-run state, not a
broken deployment. The runtime data directory (`APP_DATA_DIR`) holds logs,
uploads and settings.

## Running the tests

```
.venv/bin/python -m pytest tests/unit -q           # no database needed
.venv/bin/python -m pytest tests/integration -q    # disposable PostgreSQL
.venv/bin/python -m pytest tests/security -q
```

Integration tests build a **disposable PostgreSQL** and run the real migrations
into a test-named database (`tests/conftest.py`); they skip only when no server
can be reached, and `REQUIRE_POSTGRES=1` turns that skip into a failure for CI.
They never touch the configured application database.

Guidelines that keep the suite useful:

* **Never weaken an assertion, delete a test or broaden a skip** to get a green
  run. A failing test is either a defect in the code, a defect in the fixture, or
  a wrong expectation — say which, and fix that one.
* Prefer the repository's own generators over hand-editing a generated document
  (see "Generated documents" below); a hand edit fails the comparison test.
* Run the focused test file first, then the neighbours it touches, then the
  suite batch. A database test that "passes" against a stub has verified
  nothing: the integration suite exists so behaviour is proven against real
  PostgreSQL.

Node-based tests (the declarative-event runtime and the action-toolbar smoke
test) skip when `node` is absent. If you change front-end behaviour, run them
with node installed; do not edit them to run without it.

## Front-end conventions

The interface is server-rendered Jinja plus plain JavaScript modules under
`static/js/` (`modules/core`, `modules/<domain>`, `pages/`). Two rules are
enforced by tests, not by review:

* **No inline script.** The Content-Security-Policy is `script-src 'self'` — no
  `'unsafe-inline'`, no `eval`. Interactive attributes go through the
  declarative interpreter:

  ```html
  <button data-on-click="selectAll()">Select all</button>
  ```

  `static/js/modules/core/declarative-events.js` looks `selectAll` up on
  `window`, so the function must be reachable there (a top-level `function` or
  `var` in a classic script, or an explicit `window.selectAll = ...`; a name
  defined only inside an ES module is not). Page data travels in
  `<script type="application/json" id="...-page-data">` blocks, which the
  policy does not execute.
* **No inline event handlers anywhere** — not in a template, not generated by
  script. `tests/unit/test_csp_no_inline_script.py` scans templates, scripts
  and every page the application serves, and fails on an `on*=` attribute, an
  executable inline `<script>`, `javascript:` URLs, or a handler name that is
  not reachable on `window`.

Text is translated through `_()` in templates and the catalogues under
`translations/`; Arabic, Hebrew and Persian render right-to-left, so a new
layout must work in both directions. Static assets are referenced with
`url_for('static', filename=...)` so the served path and the file on disk cannot
drift — `tests/unit/test_static_references.py` checks that every literal
reference exists.

## Python conventions

* Layer direction is one-way: routes → services → core/database. Core and
  services never import a route.
* **Every query is parameterised.** Interpolating a value into SQL is a defect;
  `core/sql_safety.py` and `core/path_safety.py` exist so the safe form is the
  easy one.
* **Raise a typed error, answer with a status code.** Raw exception text never
  reaches a client (`core/errors.py`); log the detail server-side and return a
  client-safe message with a correlation id.
* Long-running work belongs to the job system (`services/jobs/`), not to a
  request thread. Emit events through the manager so the progress is observable
  and cancellable, and add a new event type to `job_state.EVENT_TYPES` in the
  same change — `tests/unit/test_job_event_vocabulary.py` derives the emitted
  set from the call sites and fails if the vocabulary and the writers disagree.
* Registries are the single source of truth for what exists: add an interface to
  `core/interfaces/` and an action to `core/experience/action_registry.py`
  rather than describing it in a document by hand.

## Database changes

A schema change is a new numbered migration under `database/migrations/`
(`m00NN_name.py` with `version`, `name`, `upgrade`, `downgrade`), never an edit
to an applied one — `schema_migrations` is the ledger and a rewritten migration
is a different schema depending on when a database was created. See
[DATABASE.md](DATABASE.md) and, for the audit that produced the current shape,
[database/MIGRATION_PLAN.md](database/MIGRATION_PLAN.md). Two habits worth
copying from the existing migrations:

* make the statement idempotent (`IF EXISTS` / `IF NOT EXISTS`) and keep it
  transactional, because the runner wraps each migration in a transaction;
* check the precondition before the change and **refuse loudly** if it is not
  met (a missing object, a row that would violate a new constraint) instead of
  failing halfway with a raw driver error.

## Translation catalogues

The catalogs under `translations/<lang>/LC_MESSAGES/` are the product's text, and
they are maintained by hand with two tools and three tests around them.

| Step | Command |
| --- | --- |
| Extract from the sources | `python3 scripts/initialize_translations.py` — writes `translations/messages.pot` from `babel.cfg` (Python + Jinja) with the keywords `_`, `gettext`, `ngettext`, `lazy_gettext` |
| Report the state of every catalog | `python3 scripts/catalog_maintenance.py` (`--json` for machines) |
| Restore from a catalog's own obsolete block, prune extraction artifacts, recompile | `python3 scripts/catalog_maintenance.py --write` |
| Compile (the tool does this too) | `python3 -m babel.messages.frontend compile -d translations` |
| Review translations in the interface | **Settings → Translation Management** (`Api/routes/translations.py`) |

Rules the tools and tests enforce:

* **A missing translation stays missing.** `scripts/catalog_maintenance.py` never
  copies English into an empty msgstr, never touches an approved entry, refuses
  to write when a catalog's obsolete history would shrink, and reports the
  entries that still need a human by language. English in the msgstr column is
  not a translation; `tests/integration/test_translation_coverage.py` fails on
  any empty or fuzzy entry in the offered catalogs for exactly that reason.
* **A fuzzy entry is not a translation.** When an English source changes,
  `msgmerge` keeps the *previous* translation and marks the entry fuzzy; that
  text belongs to a similar older msgid (Hebrew `Screen Inspector` carried
  "screen translations"). Restore only from an obsolete pair with the identical
  msgid and the same `%(name)s` placeholders — that is what the tool does.
* **A lookup is not a message.** A translation call may take a literal; when it
  takes something it looks up at runtime - `gettext(record["msgid"])` — the
  extractor offers the *key* as a message to every catalog (NARR-02: a
  `msgid`/`msgid_plural` pair, later carrying "side" in four languages). Read the
  value into a local first; `tests/unit/test_catalog_extraction.py` walks the AST
  of the first-party packages for that shape.
* **A prunable name must not be translatable.** The artifact vocabulary in
  `scripts/catalog_maintenance.py` is checked against a real extraction
  (`tests/unit/test_catalog_maintenance.py`), so a name that a page can actually
  show cannot stay in it.
* Plural entries keep the header's `nplurals` forms; Arabic declares six,
  Croatian three. `tests/unit/test_narrative_plurals.py` drives `ngettext`
  against the compiled catalogs per language, and
  `tests/integration/test_translation_coverage.py` compares the `.mo` with the
  `.po` so a stale compiled catalog cannot hide a missing string.

After changing a template's text, extract, translate, run
`scripts/catalog_maintenance.py --write`, then
`pytest tests/integration/test_translation_coverage.py tests/unit/test_catalog_extraction.py`.

## Generated documents

Several documents are generated from code and compared with it by a test, so a
count in prose cannot drift:

| Document | Generator |
| --- | --- |
| `docs/reference/DATABASE_SCHEMA.md` | `python3 tools/docs/generate_schema.py` (`--check` to verify) |
| `docs/INTERFACE_REGISTRY.md` | `python3 -m core.interfaces.docgen` |
| `docs/REGISTRY_EVIDENCE.md` | `python3 -m core.interfaces.evidence` |
| `docs/EXPERIENCE_CONTRACT.md` | `python3 -m core.experience.docgen` |
| `docs/ACTION_SURFACE_AUDIT.md` | `python3 -m core.experience.action_audit` |
| `docs/SCREEN_INSPECTOR_EVIDENCE.md` | `python3 -m core.experience.audit` |
| `docs/COMPONENT_LIBRARY.md` | `python3 -m core.frontend.component_audit` |
| `docs/reference/python/*.md` | `python3 tools/docs/generate_reference.py` |

Each generator splices its output between markers in the existing file, so the
hand-written half stays and the generated block is replaced. Regenerate, then
run the document's test.

## Quality gates before a change is done

```
.venv/bin/python -m pytest tests/unit -q                 # focused file first, then this
.venv/bin/python -m pytest tests/integration -q          # if it touches the database or a route
.venv/bin/python -m ruff check <changed files>
.venv/bin/python tools/licenses/check_licenses.py --quiet  # if a dependency changed
```

Then check that the diff contains nothing unrelated: a change that mixes a
repair with a refactor is hard to review and hard to revert.
