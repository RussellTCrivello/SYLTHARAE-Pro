# Round 4 / D-3 — measurements, with the runs that produced them

Every number in this file came out of a run on this machine, in this session.
Nothing here is estimated from reading code. Where a quantity was *not*
measured it says so at the end rather than being filled in with a plausible
figure.

Reproduce with:

```
# the 100 000-row database
python tools/audit/measure_scale_db.py
# request timings, statement counts, EXPLAIN (ANALYZE, BUFFERS) for the ten
# heaviest statements, N+1 counting, deep-offset pagination
python tools/audit/measure_queries.py
# stop PostgreSQL mid-ingest
python tools/audit/inject_failures.py --password <admin> --corpus /tmp/inject_corpus
# kill the web process mid-ingest
python tools/audit/inject_restart.py --server-pid <pid> --password <admin> \
    --corpus /tmp/inject_corpus/big --db file_analysis_failinject
# ingestion time versus document size
python tools/audit/measure_ingest_scaling.py --password <admin> \
    --db file_analysis_failinject
```

## Environment

| | |
| --- | --- |
| PostgreSQL | 16.2, `shared_buffers` 128 MB, `work_mem` 4 MB, `max_parallel_workers_per_gather` 2 |
| Machine | 2 vCPU, 3 GB RAM (the whole sandbox) |
| Application | Flask development server, one process, `run_web.py`, DB pool 2–10 connections |
| Scale database | `file_analysis_scale`: 100 000 `paths`, 100 000 `hashs`/`hash_contexts`, 75 000 `content_signals` (25 000 place mentions + 25 000 identifier mentions + 25 000 others) |
| Failure database | `file_analysis_failinject`, a normal bootstrap of the frozen schema |

The scale database is built by `tools/audit/measure_scale_db.py`: the frozen
migrations are applied by `bootstrap_database`, then rows are inserted directly
because generating a hundred thousand real documents would take hours and would
not change the plans. The documents themselves (26 realistic files, generated by
`tools/gen_realistic_corpus.py`) were ingested through the application's own
import endpoint into a separate database, so the ingestion numbers below come
from the real pipeline. **The scale database is therefore a plan/pagination
fixture, not an ingestion benchmark** — the two are kept apart on purpose.

## 1. Ten heaviest statements, `EXPLAIN (ANALYZE, BUFFERS)`

Measured across 33 requests, 260 statements, 3 444 ms of SQL in total. The
heaviest *distinct* statement per SQL text, as executed by the application (the
plan is for the exact text and parameters the driver sent, rendered with
`cursor.mogrify`):

| # | client ms | SQL execution ms | statement (truncated) | plan shape that matters |
| --- | --- | --- | --- | --- |
| 1 | 322 | 455 | `WITH file_term_counts AS (...) … /api/lexis/manage/files` | Seq Scan `paths` 100 000 rows + Seq Scan `hash_contexts` 100 000 → Hash Join → top-N sort of 100 000 rows |
| 2 | 204 | 254 | `SELECT p.id … COUNT(*) OVER() … FROM paths p JOIN hash_contexts …` (uncategorised count) | Nested Loop Anti Join over 100 000 rows, two sorts spilling to disk (2 736 kB + 2 336 kB) |
| 3 | 198 | 247 | `WITH f AS (...) … jsonb_build_object(…)` (`/api/reports/dashboard`) | two Seq Scans (100 000 + 100 000) → CTE Scan of 100 000 rows |
| 4 | 130 | 219 | `SELECT s.detector … GROUPING(...)` (signal facets) | Seq Scan `content_signals` 75 000 rows on **every** facet request |
| 5 | 125 | 160 | `SELECT si.name, COUNT(DISTINCT p.id) … GROUP BY` (per-side counts) | Hash Join 100 000 → sort spilling to disk (3 336 kB) |
| 6 | 124 | 146 | `SELECT s.id … FROM content_signals s … ORDER BY date_from …` | external merge sort 5 512 kB + 5 816 kB, Parallel Seq Scan on `content_signals` |
| 7 | 117 | 142 | `SELECT COUNT(*), COUNT(*) FILTER (…) …` (horizon counters) | Index Only Scan `paths` 100 000 + Seq Scan `hash_contexts` 100 000 |
| 8 | 88 | 184 | `SELECT s.detector … WHERE signal_type = ANY(...)` | Seq Scan `content_signals` 50 000 |
| 9 | 71 | 130 | `SELECT p.id, p.file_name … FROM paths p JOIN hash_contexts …` (`/files`) | Parallel Seq Scan `paths` 100 000, top-N heapsort |
| 10 | 61 | 220 | `SELECT COUNT(*), COUNT(DISTINCT s.hash_id) … WHERE EXISTS (…)` | Sort 75 000 rows in memory (3 073 kB) |

What the plans say, in one sentence each:

* **Every list and dashboard query is a sequential scan of the whole `paths` /
  `hash_contexts` table.** At 100 000 rows that is 8–12 ms of scan per table, so
  it is not yet a problem; at 10 million rows the same plans scale linearly and
  nothing in the schema stops them.
* **Sorts spill to disk** in three of the ten (2.3–5.8 MB each) because
  `work_mem` is 4 MB and the sort keys (`date_creation DESC, id DESC`,
  `date_from`) are not indexed. Change the sort columns in a query and the
  planner has no index to fall back on.
* **The facet aggregate scans all 75 000 signals for every request**, which is
  why `/api/signals` costs a constant ~200–330 ms regardless of `limit` or
  `offset` (see §4).
* The one aggregate that *does* use an index (`idx_content_signals_hash`,
  statement 10) still sorts 75 000 rows to answer `COUNT(DISTINCT hash_id)`.

## 2. The `evidence->>'kind'` JSONB filter, measured

`services/detection/signal_query.py` filters identifier kinds with
`s.evidence->>'kind' = ANY(%s)`. No index covers that expression (an expression
index would be a schema change, and the schema is frozen), so the question was
whether it is usable at scale. Measured on 75 000 signals:

| query | client ms | execution ms | plan |
| --- | --- | --- | --- |
| `/api/signals?limit=50&identifier_kind=email` | 83.6 | 26.0 | **Parallel Seq Scan on `content_signals`**, 4 166 rows matched |
| facet aggregate with the same filter | 24–28 | 23–28 | same Parallel Seq Scan |
| `/api/signals?limit=50` (no identifier filter) | 247.5 | 219 | Seq Scan for the facet aggregate |

So: **the JSONB filter itself costs about 26 ms at 75 000 signals** (two
parallel workers over 75 000 rows), roughly one tenth of what the unfiltered
facet aggregate costs. It is usable at this size. It grows linearly with the
signal count and there is no index that can help it without a schema change —
that is a fact about the plan, not a prediction.

## 3. N+1 on the list endpoints

Counting statements per request and comparing with the rows returned
(`measurements.json → n_plus_one`):

| endpoint | statements per request | rows returned | verdict |
| --- | --- | --- | --- |
| `/api/paths` (`limit` 50 and 500) | 5 | 50 / 500 | constant — no N+1 |
| `/api/lexis/manage/files` (pages 1, 2, 20) | 5 | 50 | constant — no N+1 |
| `/api/signals` (four variants) | 11 | 50 | constant — no N+1 |
| `/api/signals/horizon` | 11–13 | 0–50 | constant — no N+1 |
| `/api/sources`, `/api/sides`, `/api/places` | 5–6 | 2 / 4 / 0 | constant — no N+1 |
| `/files` (pages 1, 5, 40) | 17 | 50 per page | constant; one statement repeats 7× per request |
| `/api/lexis/manage/dashboard` | 13 | n/a | one statement repeats 5× per request |

The repeated statements were inspected: apart from `SELECT 1` (connection
proofs — 5–7 per request, which is the pool probing its connections on every
acquisition) the only repetition is a `COUNT(*)` that runs twice per `/files`
request (once for the page total and once for the filtered total). **No endpoint
was found that issues one statement per row.**

The 17 statements of `/files` are fixed regardless of page: the cost is the
number of *sections* on the page (counters, source list, side list, the page
itself), not the number of files.

## 4. Pagination at 100 000 rows

`/api/paths` pages with `offset`/`limit` (`Api/blueprints/paths.py`); `page` is
ignored by that endpoint, so the sweep below is over `OFFSET`:

| request | client ms | SQL ms | rows |
| --- | --- | --- | --- |
| `offset=0&limit=50` | 9.4 | 4.1 | 50 |
| `offset=5000&limit=50` | 10.2 | 4.4 | 50 |
| `offset=50000&limit=50` | 16.5 | 10.3 | 50 |
| `offset=99500&limit=50` | 25.9 | 18.0 | 50 |
| `offset=0&limit=500` | 17.5 | 5.3 | 500 |
| `offset=99500&limit=500` | 29.9 | 20.3 | 500 |

Deep-offset access costs about **2.7× the first page** at the end of the table
(18 ms of SQL versus 4 ms) — the expected `OFFSET` cost, still small at 100 000
rows. `limit=500` (the endpoint's maximum) costs 5–20 ms of SQL.

On `/api/signals` pagination does not matter at all: `offset=0` and
`offset=49950` cost 247 ms and 328 ms, because the facet aggregate scans every
signal before any `LIMIT` applies.

## 5. Failure injection — PostgreSQL stopped mid-ingest

`tools/audit/inject_failures.py`: 400 documents submitted through
`POST /api/import-export/batch-import`, PostgreSQL stopped with
`pg_ctl stop -m immediate` two seconds later (crash-style stop, no clean
rollback), polled every second for 15 rounds, then restarted.

What the client saw while the database was gone:

| endpoint | answers | latency |
| --- | --- | --- |
| `/health` | first answer **503** `{"status":"degraded","checks":{"database":"error: OperationalError"}}` in 4.6 ms; every later poll **hung** until the client gave up at 15 s | 4.6 ms, then >15 000 ms |
| `/api/jobs`, `/api/paths`, `/api/reports/overview`, `/api/signals` | **401** `{"code":"unauthenticated"}` within 2 ms, for all 15 rounds | ~2 ms |

After PostgreSQL was restarted: `/health` returned 200 again, and the API
answered 200 with a fresh sign-in (the pre-outage session was gone — with the
session store in the database, an outage signs every user out, which is
fail-closed and correct, but the client is not told why: it sees `401`, not
"database unavailable").

The 401s are quick because the session check cannot reach the database and
fails closed. `/health` is the endpoint that hangs: it acquires a pooled
connection, the pool retries with backoff, and the request waits for the 30 s
pool timeout — the 15 s client timeout in the harness cut it short, so the exact
worst case was not measured beyond 15 s. The process log during the run shows
the retry loop and then `Connection pool exhausted - timeout after 30s (pool
size: 10)`, so a client without a timeout would wait about 30 s per request.

Leak check: the only driver text in a response body was the *class name*
`OperationalError` in `/health`'s `checks.database` field. No message, host,
SQL or traceback crossed the wire; every `/api/*` body was a fixed JSON error.

After recovery the same session could not be reused (401), a new sign-in worked,
and a second import of 20 documents was accepted. **The database outage itself
did not corrupt state**: `paths` and `hashs` counts before the outage and after
recovery were consistent with what had been written (5 documents processed from
the first batch before the crash — see §6 for why only 5).

## 6. Failure injection — the web process killed mid-ingest

`tools/audit/inject_restart.py`: six 8 MB documents submitted, the server
signalled with `SIGTERM` while the tasks were running, the server restarted with
the same command.

| moment | paths | hashs | signals | jobs rows | job_events |
| --- | --- | --- | --- | --- | --- |
| before submit | 10 | 10 | 113 | 0 | 0 |
| at kill (after 300 s) | 10 | 10 | 113 | 0 | 0 |
| after restart | 10 | 10 | 113 | 0 | 0 |
| 10 s later | 10 | 10 | 113 | 0 | 0 |

* **Nothing was resumed.** The queued work lived in the process's task manager
  (a dictionary of threads); `SIGTERM` removed it, and the restart had no record
  that anything had been queued. The `jobs` / `job_events` tables were never
  written by this path, so `GET /api/jobs` answered `{"jobs": [], "success":
  true}` throughout — the UI cannot show an interrupted import because no row
  for it exists.
* **No partial rows were left behind**: ingestion writes the `paths` row only
  after the document has been analysed, so a kill before that point leaves
  nothing to clean up (and nothing to resume). No orphan `hashs` rows.
* The kill was **not observed mid-write** in this run for a different reason:
  the six 8 MB documents had produced no row after 300 s. §7 explains that with
  a measured curve rather than an assumption.

## 7. Ingestion time versus document size

Each document submitted alone through `POST /api/import-export/batch-import` to
an empty-ish database, timing until its `paths` row was committed:

| document size | seconds until row | signals written | signals per KB |
| --- | --- | --- | --- |
| 128 KB | 2.0 | 4 522 | 35 |
| 256 KB | 4.1 | 9 044 | 35 |
| 512 KB | 8.3 | 18 081 | 35 |
| 1 MB | 25.1 | 36 163 | 35 |
| 2 MB | 80.1 | 72 318 | 35 |
| 4 MB | 321.2 | 144 635 | 35 |

Through 512 KB the time is linear in size (about 16 ms per KB, doubling size
doubles time). Past that point the curve turns up and keeps turning:

| step | size factor | time factor |
| --- | --- | --- |
| 128 → 256 KB | ×2 | ×2.05 |
| 256 → 512 KB | ×2 | ×2.02 |
| 512 KB → 1 MB | ×2 | ×3.0 |
| 1 → 2 MB | ×2 | ×3.2 |
| 2 → 4 MB | ×2 | ×4.0 |

Each doubling of the document costs 3–4× the time beyond 512 KB, so the cost
grows roughly with the cube of the size in that range. The 8 MB document that
was still running after 300 s in §6 sits on this curve: at the 4 MB cost
(321 s) a further doubling by that factor is ~20–40 minutes, well past the
configured 1200 s file-processing timeout, so it would be aborted rather than
finish. The 4 MB run itself needed **321 s** — it *does* finish, it is the size
that is the problem, not a stuck pipeline.

Two measured side-effects of the size:

* **Signal amplification is 35 signals per KB, constant.** A 2 MB document
  writes 72 318 `content_signals` rows; an 8 MB document would write ~290 000.
  The stored-signal volume is two orders of magnitude larger than the input.
* The document is not slow because of the database: the `paths` row appears
  only at the end, and the task stays `running` with no row at all while the
  analysers work.

Where the time goes, from the server log of the same runs (timestamps of the
pipeline's own log lines, one run per size — an observation, not a profile):

| document | read | content extracted | storage starts → places detector | → "document processed" | total |
| --- | --- | --- | --- | --- | --- |
| 2 MB | 11 ms | 1 s | 18 s | 61 s | 80 s |
| 4 MB | 26 ms | 3 s | 70 s | 247 s | 321 s |

Reading and extraction are negligible. The signal/word analysis inside
`contents_db_service` — the steps between "storing to database" and "document
processed" — accounts for essentially all of it, and it grows faster than the
words per document (496 292 words at 4 MB against 248 148 at 2 MB, but 247 s
against 61 s).

## 9. What was **not** measured

* Concurrency: every request above was issued one at a time from one client.
  Nothing here says how these plans behave with 10 or 50 parallel clients.
* Rows beyond 100 000: the linear scans are measured at 100 000 only.
* Per-analyser timings: the phase boundaries above come from log timestamps,
  not from instrumenting each detector, so which *specific* detector dominates
  is still unmeasured.
* Ingestion above 4 MB: the 8 MB document was observed only as "still running
  at 300 s" before it was killed; it was not run to completion or to its
  timeout.
* Which analyser dominates ingestion time (no per-phase timings were taken).
* The 1200 s processing timeout was not waited for, so the abort path for an
  oversized document is unverified.
* Write throughput and WAL behaviour under bulk ingest.
* Network latency: the client and the server share the machine, so all client
  timings exclude network delay.
