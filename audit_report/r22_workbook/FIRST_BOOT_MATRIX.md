# First-boot matrix — the revived scheduler (B)

Generated by `tools/audit/r22_first_boot.py` from a live database
(`run_migrations` applied the frozen chain; no migration was added).
The behavioural half of each row is proved by
`tests/integration/test_scheduler_first_boot_pg.py`.

## The default: a database with no schedule rows

| question | answer | evidence |
|---|---|---|
| does anything fire? | no: no timers are registered | `test_an_empty_schedule_table_starts_and_registers_nothing` |
| what would fire if a row existed? | the table below | `test_the_first_boot_matrix_covers_every_schedulable_type` |
| is a fire observable before it deletes? | yes: the job row names the schedule and its `result_summary` carries the per-area counts | `test_the_first_fire_is_observable_before_it_deletes_anything` |
| can two processes both fire? | no: one holds the advisory lock and the other declines | `test_two_instances_do_not_both_fire` |
| does stopping the process stop the timers? | yes: `stop()` shuts the scheduler down and releases the lock; a hard exit releases it with the connection | `test_exiting_the_process_stops_the_scheduler_and_frees_the_lock` |
| does a **SIGKILLed** leader block the next boot? | no: the lock is the connection, so the kill frees it; a second runner declines while the leader lives and leads within the retry window after `SIGKILL` | `test_a_sigkilled_leader_releases_the_lock_and_the_next_one_leads` |

## What each schedulable type does by default

| type | default state | first fire |
|---|---|---|
| `scenario_evaluation` | disabled (no rows exist until one is created) | evaluates every active scenario |
| `retention` | disabled (no rows exist until one is created) | audit_log: kept forever; jobs: deletes rows older than 90 days; notifications: kept forever; path_revisions: kept forever; scenario_outcomes: kept forever |

## What a first fire can delete, area by area

| area | table | default days | deleted by a first fire | status guard |
|---|---|---|---|---|
| `audit_log` | `audit_log` | 0 | nothing - keep forever | none |
| `jobs` | `jobs` | 90 | finished jobs and their events (job_events cascade), older than 90 days | status NOT IN ('QUEUED', 'RUNNING', 'PAUSED') |
| `notifications` | `alerts` | 0 | nothing - keep forever | none |
| `path_revisions` | `path_revisions` | 0 | nothing - keep forever | none |
| `scenario_outcomes` | `scenario_outcomes` | 0 | nothing - keep forever | none |

Every area but `jobs` is keep-forever by default, and `jobs` is guarded against live rows, so the worst a first fire can do to a new database is remove finished job history older than 90 days.

## How a stored payload becomes a job's options

| type | stored key the page writes | option the job reads | keys with no counterpart |
|---|---|---|---|
| `scenario_evaluation` | `scenario_id` | `scenario_ids` | `version` - the job evaluates the active definition |
| `retention` | `policy` | `areas` | none - `max_age_days` is not an input to the job; the policy days come from the settings |

## Configuration

`SYLTHARAE_SCHEDULER` is read in exactly one place (`services/scheduling/scheduler.py:enabled_by_config`) and set in exactly one place that is not a test: `run_web.py`, with `setdefault('SYLTHARAE_SCHEDULER', '1')`. `grep -rn SYLTHARAE_SCHEDULER --include=*.py` returns four hits: the setter, the reader, and two comments. No test sets it, so the suite runs with the default (off).
