## What stands in front of an automatic write

| guard | what it does |
|---|---|
| rule validation | a workbook that breaks a rule is refused; nothing is written |
| shrink limit | `SYLTHARAE_TAXONOMY_SHRINK_MAX` (default 0.25, floor 25 rows): a sync that would remove more than that share of the stored memberships and keywords is refused, with the numbers in the message. A deliberate large removal sets it to 1, and the run reports the limit it overrode |
| apply lock | an advisory lock on the apply path only: two instances booting together cannot both write, and the second reports `already_syncing` |
| fingerprint | workbook bytes + the rule sources + `SYNC_LOGIC_VERSION`; a changed rule makes the same file mean something else, so the fast path cannot skip it |

Measured: the unchanged path costs 0.42 ms, the slow path 56.5 ms for a
30-category workbook (`tests/integration/test_startup_sync_guards_pg.py`).

**NEEDS-DECISION - the workbook's own schedule type.** The obvious next
step, a `taxonomy_sync` schedule that applies the workbook every N minutes,
is blocked by the schema, not by code:

CHECK (schedule_type IN ('scenario_evaluation', 'retention'))

Allowing a third value is a migration, which the standing rule forbids
without explicit authorisation. Everything on this side is ready for it:
the job type exists, the service exists, and
`tests/integration/test_scheduler_wiring.py` asserts that the vocabulary and
the constraint agree - so the migration and the Python change have to land
together, and the test says so if they do not.
